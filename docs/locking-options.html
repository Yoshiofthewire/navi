Locking choices for Navi

My pick: swaylock. It fits Navi’s existing shared-memory rendering and keeps the first implementation small. The lock core belongs in Navi whichever password screen we choose.

OptionWhat you get / trade-off for Navi
swaylock

Default

Plain color or image, configurable colors and password feedback. PAM authentication.

Trade-off: Least additional integration beyond session-lock. Cairo and shared-memory buffers; limited widget-style customization.

waylock

Plain

Three-color feedback and PAM. No image toolkit or GPU renderer in its manifest.

Trade-off: Current upstream also requires viewporter and single-pixel-buffer protocols. Navi must add those; no images, clock or widgets.

gtklock

GTK

GTK3 widgets, CSS and optional modules. Uses the real session-lock protocol.

Trade-off: Adds GTK and gtk-session-lock. Upstream is seeking a maintainer; verify selected modules and packaged version.

hyprlock

Rich

Blur, images, widgets, animations, PAM and native fprintd support. Not restricted to Hyprland’s private lock API.

Trade-off: Larger graphics/library stack. Client EGL needs testing; live screenshot backgrounds need capture support Navi lacks.

Choose swaylock for the shortest path; waylock for an intentionally plain screen. Choose gtklock or hyprlock when their added UI features are worth the integration work.

What about KDE, GNOME, COSMIC, Rust and other lockers?
  • KDE / GNOME: desktop-integrated lock architectures, not drop-in password windows for Navi.
  • COSMIC: a real Rust session-lock client, but its libcosmic/services dependencies need a separate compatibility trial.
  • Quickshell: provides QtQuick session-lock primitives; a chosen shell still owns authentication and unlock correctness.
  • Custom Navi Rust locker: full control, with the greatest credential-handling and UI maintenance burden.
  • Rust alternatives: swaywardlock is beta; Amorphis warns that it is early-stage. Not the default recommendation.
  • swaylock-effects: the familiar upstream forks are stale or explicitly unmaintained; newer forks need review rather than assumed safety.
  • X11-only lockers: cannot secure native Wayland clients. Current XScreenSaver Wayland support was not verified.
  • loginctl / swayidle / wayidle: coordinate locking or idle events; they do not supply the secure lock and password UI themselves.

Shared work required for every choice

Navi must protect every monitor and route input only to the locker, stay locked after a locker crash, and wait for confirmed lock coverage before Sleep or Switch User. Smithay already provides the protocol plumbing; Navi still needs the policy and tests.

Research checked 5 Nov 2026. Source review only: no candidate has been installed or run as Navi’s locker. No measured CPU/RAM ranking is available. Launching the locker on demand avoids a permanently running locker process.
